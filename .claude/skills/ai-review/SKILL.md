# AIレビュー（検出→検証の2段構成）

このスキルは、自分で直接レビューせず、**検出エージェントと検証エージェントを呼び分ける司令塔**として動く。
自分でコードを読んで指摘を追加・修正してはいけない。削除してよいのは、手順 3 の判定と手順 4 の統合によるものだけ。

**ここに書かれていない手順を足さない。** 特に次のことはしない。

- サブエージェントへの聞き直しや追加の指示（`SendMessage` など）。応答が期待した形でなければ、下の手順に書かれた扱い（失敗、または DROP）にする
- シェルでのループ、リダイレクト、パイプ、`&&`。許可ルールに合わず拒否される。ファイルの存在確認は Glob で行う
- サブエージェントのバックグラウンド実行と、その完了を待つための待機（`ScheduleWakeup` など）。
  **Agent ツールは必ず `run_in_background: false` を指定して呼び、結果が返るまで待つ。**
  CI は非対話で動くので、バックグラウンドの完了を待たずに最終出力を返すと、その時点でセッションが終わり、結果は失われる

参照ファイル（パスはリポジトリルートから）:

- 共通の前提: `.claude/skills/ai-review/references/common.md`（すべての検出役と検証役が読む）
- ルール定義: `.claude/skills/ai-review/references/rules.md`（規約準拠の検出役と、`DEF-` / `SEC-` などのルール ID の指摘の検証役だけが読む）
- テストのルール定義: `.claude/skills/ai-review/references/test-rules.md`（テストの検出役と、`TEST-` で始まるルール ID の指摘の検証役だけが読む）

仕組みと運用は `docs/ai-review.md`。

## 観点

| 観点 | 検出役（`subagent_type`） | 対象ファイル | 指摘の `rule_id` |
| --- | --- | --- | --- |
| 規約準拠 | `review-detector-rules` | 本体 | `rules.md` のルール ID |
| セキュリティ | `review-detector-security` | 本体 | `SECURITY` |
| テスト | `review-detector-tests` | 本体とテスト（backend と frontend） | `test-rules.md` のルール ID。どれにも当たらないものは `TESTS` |

## モード

- **CIモード**: プロンプトに `MODE: ci` と `PR NUMBER` が含まれる場合（`BASE REF` も含まれる）。結果をJSONとして最終出力に返す。**PRへの投稿はしない**（投稿はワークフローの後続ステップが行う）。
- **ローカルモード**: それ以外。結果を画面に表示するだけで、どこにも投稿しない。

## 手順

### 1. 差分の範囲を決める

- CIモード: `gh pr diff <PR NUMBER> --name-only` で変更ファイル一覧を取る。
- ローカルモード: `git diff --name-only origin/main...HEAD` と `git diff --name-only`（未コミット分）を合わせる。

変更ファイルから、次の 4 つの一覧を作る。どれも、作業ツリーに存在するもの（削除されたファイルは除く）だけ。Glob で確かめる。

- **本体**: `backend/src/main/java/` 配下の `.java` ファイル
- **テスト**: `backend/src/test/java/` 配下の `.java` ファイル
- **frontend の本体**: `frontend/src/` 配下の `.ts` / `.tsx` ファイルのうち、`.test.ts` / `.test.tsx` でないもの。`frontend/src/lib/api/schema.d.ts`（生成物）は除く
- **frontend のテスト**: `frontend/src/` 配下の `.test.ts` / `.test.tsx` ファイル

自動生成コード（`build/`、`generated/` 配下、`schema.d.ts`）と、上のどれにも当たらないファイルはどの一覧にも入らない。

4 つとも 0 件なら、指摘0件として手順5へ進む。

### 2. 検出

3 つの観点の検出役を、**すべて 1 つのメッセージで並列に**呼ぶ（Agent ツール。どれも `run_in_background: false`）。

- 規約準拠とセキュリティ: 対象は**本体**（backend だけ）。本体が 0 件なら呼ばない
- テスト: 対象は**本体・テスト・frontend の本体・frontend のテスト**。4 つとも 0 件なら呼ばない
- 対象ファイルが 8 個を超える観点は、ファイルを 8 個以下のグループに分けて、グループごとに 1 体呼ぶ

以下、「観点 × グループ」の 1 回の呼び出しを **検出グループ** と呼ぶ。

渡す内容は次だけ。変更の意図や、危なそうな箇所の見立ては渡さない。**他の観点の結果も渡さない。**

- 対象ファイル一覧
- 差分の取得方法（CIなら `gh pr diff <PR NUMBER>`、ローカルなら `git diff origin/main...HEAD` と `git diff`）
- 共通の前提のパス
- 規約準拠のみ: ルール定義のパス
- テストのみ: ベースブランチ（CIなら `origin/<BASE REF>`、ローカルなら `origin/main`）と、テストのルール定義のパス

各エージェントが返したJSONの `findings` をすべて集める。

次の応答は、その検出グループの**検出に失敗した**ものとして数える（**失敗グループ数**）。聞き直さない。

- JSON として読めない
- `{"error": ...}` を返した
- `findings` キーが無い

失敗したグループの `findings` は 0 件として扱う。**失敗を「指摘なし」として扱ってはいけない**（そのために失敗グループ数を出力に含める）。

成功したグループの件数の合計を **検出件数**（`detected_count`）として控えておく。0件なら手順5へ進む。

### 3. 検証

集めた指摘**1件ごとに** `review-verifier` エージェントを1つずつ呼ぶ（`subagent_type: review-verifier`、`run_in_background: false`。1つのメッセージで並列に呼んでよい）。

渡す内容は次だけにする。**検出エージェントの思考過程や他の指摘は渡さない。**

- 指摘のJSON1件
- 共通の前提のパス
- `rule_id` がルール ID（`SECURITY` / `TESTS` 以外）のときだけ: ルール定義のパス。`TEST-` で始まるならテストのルール定義、それ以外なら `rules.md`
検証役に先入観を持たせないため。

応答の1行目が、前後の空白を除いて `VERDICT: KEEP` と完全に一致するものだけを残す。
1行目がそれ以外の形式（`VERDICT: DROP`、空行、説明文など）なら DROP 扱いにする。

- 本文のどこかに `VERDICT: KEEP` が書かれていても、1行目でなければ DROP。読み取って救済しない
- 検証役に聞き直さない。形式の崩れた応答が多ければ、それは検証役の定義を直すべきというデータになる

残った件数を **検証通過件数**（`verified_count`）として控えておく。

DROP にした指摘は捨てずに、**落とした指摘**（`dropped`）として次の形で控えておく。人が 1 回目のレビューで拾えるように、サマリに畳んで出すため。

- `rule_id` / `file` / `line` / `issue`: 検出役の指摘のまま。書き換えない
- `reason`: 検証役の応答の **2 行目**をそのまま使う。要約し直さない
  - 1 行目の形式が崩れていて DROP 扱いにしたものは、`reason` を `検証役の応答の形式が崩れていた` にする

### 4. 集約

- **観点をまたいだ指摘は統合しない。** 同じファイルの同じ行でも、`rule_id` が違えば別の指摘として残す。
  観点が違えば、同じ行でも中身は別の問題であることが多い（例: セキュリティの「ハッシュの露出」と、テストの「そのエンドポイントのテストが無い」）。
- 同じ `rule_id` で同じファイルの指摘が複数あれば、行番号が最も小さいものを代表の1件にし、他の該当行を `issue` の末尾に「同様の箇所: 58行目、73行目」のように追記する。
- 重要度順（high → medium）に並べる。同じ重要度の中では、ファイルパス、行番号の順。
- 件数の上限による絞り込みはしない（CIではワークフロー側で行う）。

### 5. 出力

#### CIモード

PRへの投稿や `gh` によるコメントは**行わない**。次の形のJSONを最終出力として返す。
スキーマは呼び出し側で指定されているので、それに従うこと。

```json
{
  "detected_count": 7,
  "verified_count": 5,
  "failed_groups": 0,
  "dropped": [
    {
      "rule_id": "TESTS",
      "file": "backend/src/main/java/com/example/readinglog/book/BookController.java",
      "line": 74,
      "issue": "数値でない id を渡したときの振る舞いを確かめるテストが無い。",
      "reason": "今の実装は標準のハンドラで 400 を返しており、退行が見逃される経路を示せない。"
    }
  ],
  "findings": [
    {
      "rule_id": "DEF-001",
      "severity": "high",
      "file": "backend/src/main/java/com/example/readinglog/book/BookService.java",
      "line": 42,
      "issue": "同一クラス内の register() から REQUIRES_NEW 付きの saveHistory() を呼んでおり、プロキシを経由しないため新しいトランザクションが開始されない。",
      "suggestion": "saveHistory() を別の Bean に切り出し、そちらを注入して呼び出す。"
    }
  ]
}
```

- `detected_count`: 手順2の検出件数（検証前。失敗したグループの分は含まない）
- `verified_count`: 手順3の検証通過件数（手順4の統合の前）
- `failed_groups`: 手順2で検出に失敗した検出グループの数（観点をまたいで合計）。全部成功したら 0
- `dropped`: 手順3で DROP にした指摘。0件なら空配列。手順4の統合はしない
- `findings`: 手順3・4を経て残った指摘。0件なら空配列。検出役の `id` は含めない
- `file`: リポジトリルートからの相対パス
- `line`: 新しいコード側の行番号

#### ローカルモード

残った指摘を、ファイル名・行番号・ルールID・重要度・内容・修正案の形で一覧表示する。
最後に「検出 N件 → 検証通過 M件（統合後 K件）」を表示する。次があれば、それも書く。

- 観点ごとの検出件数と検証通過件数
- 検出に失敗した検出グループ（観点とファイル）と、その理由
- 1行目の形式が崩れていたために DROP 扱いにした検証の件数
- 検証で落とした指摘の一覧（ファイル・行番号・ルールID・内容・落とした理由）

# AIレビュー ルール定義

検出役（`review-detector`）と検証役（`review-verifier`）が共通で読むルール定義。
**ここに書かれたルールに当てはまるものだけを指摘する。**

## 対象外（他のツールや人間に任せるもの）

次の観点は、どのルールにも含めない。検出役も検証役も、これらを理由に指摘しない。

| 観点 | 担当 |
| --- | --- |
| フォーマット（インデント、改行、import 順、未使用 import） | Spotless（`make lint-backend`） |
| 命名 | 人間のレビュー。`backend/CLAUDE.md` の命名規約 |
| レイヤ依存（Controller → Service → Mapper の方向、acting user の渡し方） | 人間のレビュー。ArchUnit は MVP 期間中は導入しない（`CLAUDE.md`） |
| テストの成否、テストの有無、カバレッジ | `make test-backend`（CI の static-checks ジョブ） |
| API 契約と `docs/openapi.json` のずれ | `OpenApiSnapshotTest` |
| テストコード（`src/test/` 配下） | 今回は対象外。必要になったらルールを追加する |

## 共通ルール

1. **どのルールにも当てはまらない指摘は出さない。** 一般的なベストプラクティス、好み、リファクタリング提案は、正しくても出さない。
2. **「かもしれない」だけの指摘は出さない。** 問題が起きる具体的な経路（どの呼び出しで、どの値のとき、何が起きるか）をコードで示せるものだけを出す。
3. **修正案は具体的に示す。** 「見直してください」「検討してください」ではなく、何をどう変えるかを書く。
4. **変更された行だけを指摘する。** 差分に含まれない既存コードの問題は、同じルールに当てはまっても出さない。

## 次元

| 次元 | 意味 |
| --- | --- |
| DEF | コード欠陥。実行時に意図と違う動作をする |
| SEC | セキュリティ。攻撃者が悪用できる |
| PERF | パフォーマンス。**MVP 期間中はルールを置かない**（`CLAUDE.md`「パフォーマンス最適化をやらない」）。次元だけ予約しておく |

## DEF-001 同一クラス内からの `@Transactional` メソッド呼び出し

- **重要度**: high
- **背景**: Spring の `@Transactional` はプロキシで実現される。同じクラスの中から `this.method()`（暗黙の `this` を含む）で呼ぶとプロキシを経由しないため、呼び出し先の `@Transactional` の設定は効かない。

### 指摘すること

- 同じクラスのメソッドから、`@Transactional` が付いたメソッドを直接呼んでいて、**呼び出し先の設定が呼び出し元と違う**ために意図した動作にならない場合。例:
  - 呼び出し元にトランザクションが無く、呼び出し先の `@Transactional` でトランザクションを開始するつもりでいる
  - 呼び出し先が `propagation = REQUIRES_NEW` / `NESTED` / `NOT_SUPPORTED` で、別のトランザクションになるつもりでいる
  - 呼び出し先が `readOnly = false` で、呼び出し元が `readOnly = true`（呼び出し先の書き込みが読み取り専用のトランザクションで実行される）
  - 呼び出し先の `rollbackFor` / `noRollbackFor` / `timeout` / `isolation` に依存している
- クラスに付いた `@Transactional` と、メソッドに付いたものとの組み合わせでも同じ。

### 指摘しないこと

- 呼び出し元と呼び出し先の `@Transactional` の設定が同じで、呼び出し元のトランザクションにそのまま参加すれば足りる場合（プロキシを経由しなくても動作は変わらない）。
- 呼び出し元にトランザクションが無く、呼び出し先が**単一の SQL 文**しか実行しない場合。単一の文は自動コミットでも原子的に実行されるので、`@Transactional` が効かなくても結果は変わらない（呼び出し先が `readOnly` / `timeout` / `isolation` などの設定に依存している場合は除く）。
- 別の Bean を注入して呼んでいる場合（`otherService.method()`）。注入された自分自身（self-injection）や `AopContext.currentProxy()` 経由の呼び出しも含む。
- `@Transactional` が付いていないメソッドの呼び出し。
- `private` メソッドに `@Transactional` が付いている場合。これは自己呼び出しとは別の問題なので、このルールでは出さない。
- Controller や Mapper に `@Transactional` が付いていること自体（レイヤ規約の問題。対象外）。

### 修正案の例

呼び出し先を別の Bean に切り出して注入する。または、呼び出し元に必要な `@Transactional` を付けて、呼び出し先の設定に依存しないようにする。

## DEF-002 例外の握りつぶし

- **重要度**: medium
- **背景**: 例外を捕まえて何もしないと、失敗が成功として扱われ、原因の調査もできなくなる。

### 指摘すること

- `catch` ブロックで、次の**すべて**に当てはまる場合:
  - 例外を再送出しない（ラップしての送出も含めて、送出しない）
  - 例外をログに出さない
  - 失敗を呼び出し元に伝える値を返さない
  - これらをしない理由がコメントに書かれていない
- `catch` で `null` や空のコレクション、デフォルト値を返しているが、**呼び出し元がそれを正常値と区別できない**ために、失敗が成功として扱われる場合。
- `@Transactional` メソッドの中で、例外を捕まえて正常に return しているために、書き込みの途中で失敗してもロールバックされずにコミットされる場合。

### 指摘しないこと

- 例外を別の例外にラップして送出している場合（`throw new XxxException(..., e)`）。
- `log.warn` / `log.error` などで例外を出力している場合。ログのレベルの妥当性は問わない。
- 失敗を表す値を返し、呼び出し元がそれを処理している場合（`Optional.empty()` を返し、呼び出し元が空を処理している、など）。
- `catch` の中に、握りつぶす理由を説明するコメントがある場合（例: `// 存在しなければ作成済みとみなす`）。
- `InterruptedException` を捕まえて `Thread.currentThread().interrupt()` を呼んでいる場合。
- `@ExceptionHandler` / `@ControllerAdvice` の中で、例外をエラーレスポンスに変換している場合。
- try-with-resources の `close()` の失敗だけを無視している場合。

### 修正案の例

呼び出し元に処理させるなら、ドメイン例外にラップして送出する（`common/error/` の `DomainException` 系）。処理を続けるのが正しいなら、ログに出したうえで理由をコメントに書く。

## SEC-001 MyBatis の `${}` による SQL の文字列連結

- **重要度**: high
- **背景**: MyBatis の `#{}` はバインド変数（PreparedStatement のプレースホルダ）になる。`${}` は値をそのまま SQL 文字列に埋め込む。外部から入った値が `${}` に届くと SQL インジェクションになる。このプロジェクトの SQL は Mapper インターフェースのアノテーション（`@Select` など）に書かれている。

### 指摘すること

- `@Select` / `@Insert` / `@Update` / `@Delete` / `@SelectProvider` などの SQL の中で `${...}` を使っていて、その値が**リクエストのパラメータ、リクエストボディ、ヘッダなど外部の入力から来る経路**がある場合。
  - 経路は、呼び出し元の Service から Controller まで Grep で辿って示す。
- `@SelectProvider` などの Provider クラスや `SQL` ビルダーで、外部の入力を文字列連結して SQL を組み立てている場合。
- **指摘の位置（`file` / `line`）は、`${}` が書かれた行にする。** 注入の経路は 1 つの問題なので、
  Service などで SQL の断片を文字列連結している行があっても、別の指摘にしない。連結している箇所は `issue` の経路の説明に含める。
  （Provider クラスの場合は、外部の入力を連結している行を位置にする）

### 指摘しないこと

- `#{...}` を使っている場合（バインド変数なので安全）。
- 同じ注入経路を、`${}` の行とは別の行（Service での文字列連結など）で指摘する場合。上の「指摘の位置」に従って 1 件にまとめる。
- `${}` の値が、コード上で固定の集合に限られていることを示せる場合。例:
  - `enum` の `name()` や定数から来ている
  - ホワイトリストの `Map` / `switch` で検証済みの `ORDER BY` の列名
- `${}` の値の出どころが、設定ファイルやコードの定数だけの場合（外部の入力が届かない）。
- 認可（`user_id` の条件が無いなど）の問題。このルールはインジェクションだけを扱う。

### 修正案の例

値を `#{}` に変える。`ORDER BY` の列名のように `#{}` にできない値は、`enum` やホワイトリストで検証してから `${}` に渡す。

# AIレビュー 共通の前提

すべての検出役（規約準拠・セキュリティ・バグ・テストの骨抜き）と検証役が読む。

## 対象外（他のツールや人間に任せるもの）

次の観点は、どの検出役も指摘しない。検証役は、これに当たる指摘を DROP にする。

| 観点 | 担当 |
| --- | --- |
| フォーマット（インデント、改行、import 順、未使用 import） | Spotless（`make lint-backend`）、Prettier と ESLint（`make lint-frontend`） |
| 命名 | 人間のレビュー。`backend/CLAUDE.md` の命名規約 |
| レイヤ依存（Controller → Service → Mapper の方向、acting user の渡し方） | 人間のレビュー。ArchUnit は MVP 期間中は導入しない（`CLAUDE.md`） |
| 型の誤り（frontend） | `tsc`（`make lint-frontend`） |
| テストの成否、カバレッジの数値 | `make test-backend` / `make test-frontend`（CI の static-checks ジョブ） |
| API 契約と `docs/openapi.json` のずれ | `OpenApiSnapshotTest` |
| パフォーマンス | MVP 期間中はやらない（`CLAUDE.md`） |

## 共通の原則

1. **「かもしれない」だけの指摘は出さない。** 問題が起きる具体的な経路（どの呼び出しで、どの値のとき、何が起きるか）をコードで示せるものだけを出す。
   テストのルール（`TEST-001`〜`TEST-005`）とテストの骨抜き（`HOLLOW`）では、この「経路」の意味が違う。下の「テストの観点での経路」「骨抜きの観点での経路」に従う。
2. **修正案は具体的に示す。** 「見直してください」「検討してください」ではなく、何をどう変えるかを書く。
3. **変更された行だけを指摘する。** 差分に含まれない既存コードの問題は出さない。
4. **一般的なベストプラクティス、好み、リファクタリング提案は出さない。** 正しくても出さない。

## テストの観点での経路

テストの穴の指摘は、いつも「今は正しく動くコード」についての指摘になる。「今の実装で壊れる経路」を求めると、どのテストの指摘も落とせてしまう。
そのため、確かめられていない振る舞いを指摘するテストのルール（`TEST-001`〜`TEST-005`）では、原則 1 の「経路」を**退行が見逃される経路**として読む。示すのは次の 4 つ。

1. **どの行か**: 差分で追加・変更された、特定の行。
2. **どう変わるか**: その行への、ありそうな 1 か所の編集（条件を消す、列を足す・消す、アノテーションを外す、など）。
3. **何が壊れるか**: その編集で変わる振る舞い。**差分のコード・javadoc・API 契約が約束している振る舞い**に限る。
4. **なぜ気づけないか**: その編集をしても、どのテストも落ちないこと。`backend/src/test/`（frontend なら `frontend/src/` の `*.test.ts` / `*.test.tsx`）を Grep して示す。

- **「今の実装は正しい」は、テストの観点では指摘を落とす理由にならない。**
- 次のものは出さない（検証役は DROP にする）。
  - 差分の外にある行の編集を前提にするもの。
  - まだコードに無い機能（後のマイルストーンで入る予定のもの）を前提にするもの。約束しているのが差分のコードや javadoc なら、この除外には当たらない。
  - 不自然な壊し方を前提にするもの。複数のファイルにまたがる改変、フレームワークの設定や継承を外す、など。
- **弱められたテストは、この 4 つを満たさなくても出す。** 差分が既存のテストを削除・無効化したり、要求先を付け替えたりして、それまで確かめていた経路が確かめられなくなった場合。変更前のテストを `git show` で引用して示す。

## バグの観点での正しさの出どころ

バグ（`BUGS`）の指摘は「意図と違う結果になる」ことを示す。**意図**は次のどれかから読み取れるものに限る。仕様書や Issue は渡されないので、推測で補わない。

- 差分のコードの名前（メソッド名、変数名、定数名）と、javadoc・コメント
- API 契約（`docs/openapi.json`、`frontend/src/lib/api/schema.d.ts`）と、DB のスキーマ（`backend/src/main/resources/db/migration/`）
- 同じ差分の中の、その値を使う側・渡す側のコード（呼び出し元が `null` を想定していない、など）
- 差分のテストが期待している振る舞い

示すのは、**どの入力・状態のとき**、**どの呼び出しで**、**何が起き**、**本来どうなるべきか（上のどれが根拠か）**の 4 つ。

- 次のものは出さない（検証役は DROP にする）。
  - 今のコードのどこからも来ない入力を前提にするもの（呼び出し元が常に検証済みの値を渡している、DB の制約で起きない、など）。
  - 意図の根拠が上のどれにも無く、「普通はこうすべき」でしか言えないもの。

## 骨抜きの観点での経路

テストの骨抜き（`HOLLOW`）の指摘は、「テストは Green だが、確かめたと称する振る舞いを確かめていない」ことを示す。型ごとに次を示す。

| 型 | 示すこと |
| --- | --- |
| 意味のない通るテスト | そのテストが確かめたと称する本体のコードに、**ありそうな 1 か所の誤った編集**（条件を反転する、戻り値を変える、処理を消す）をしても、そのテストの検証がすべて通ること。検証の行を引用して示す |
| ダミー返却 | テスト名・javadoc が確かめると言っている処理が、どこで偽物・固定値に差し替えられているか。その結果、本物の処理がそのテストで一度も実行されないこと |
| 意図的なスキップ | スキップの条件（または実行対象から外れる理由）と、それが CI（`.github/workflows/`）とローカルの `make test` で成立しない・外れることの根拠 |

- **「他のテストが確かめている」なら出さない。** 骨抜きのテストがあっても、同じ振る舞いを別のテストが確かめていれば、退行は見逃されない。`backend/src/test/`（frontend なら `frontend/src/` の `*.test.ts` / `*.test.tsx`）を Grep して示す。
- 次のものは出さない（検証役は DROP にする）。
  - `test-rules.md` の「frontend での境界」やアプリ外の依存を差し替えていて、差し替えた先にテストが確かめたと称する処理が入っていないもの。
  - 理由のコメント付きで一時的に止めていて、Issue やマイルストーンが書かれているスキップ（`@Disabled("M3 で API ができたら有効にする #21")` など）。

## 観点と ID

| 観点 | 検出役 | 指摘の `rule_id` |
| --- | --- | --- |
| 規約準拠 | `review-detector-rules` | `rules.md` のルール ID（`DEF-001` など）と、`test-rules.md` のルール ID（`TEST-001` など） |
| セキュリティ | `review-detector-security` | `SECURITY` |
| バグ | `review-detector-bugs` | `BUGS` |
| テストの骨抜き | `review-detector-hollow-tests` | `HOLLOW` |
